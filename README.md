# Сверка условий договоров поставки

Прототип для специалиста по закупкам: загружает TXT-документы по поставкам и показывает по каждому договору сумму и срок поставки на дату проверки. У каждого значения есть дословная цитата и переход к абзацу исходного текста. Условия меняет только подписанное допсоглашение, вступившее в силу к дате проверки; письма и проекты показаны отдельно, как несогласованные предложения.

**Открыть:** https://olshanskiyad.github.io/supply-terms-checker/

## Запуск

Зависимостей нет, сервер не нужен: весь разбор идёт в браузере.

- По ссылке выше: нажать «Учебный комплект (6 файлов)» или загрузить свои TXT кнопкой «Загрузить TXT».
- Локально: скачать репозиторий и открыть `index.html` в браузере, файлы загрузить кнопкой из папки `documents`.
- Локально с кнопкой учебного комплекта: `python3 -m http.server 8000` в папке проекта, открыть http://localhost:8000
- Тесты (Node.js 18+): `node --test`

## Как пользоваться

1. Загрузить файлы. Дата проверки по умолчанию 10.03.2026, её можно поменять, таблица пересчитается.
2. Таблица: договор, поставщик, сумма, срок, несогласованные предложения. Если значение изменено допсоглашением, видно каким и что было раньше. Ссылка под значением ведёт к абзацу документа и подсвечивает его.
3. Вопросы: четыре кнопки с вопросами закупщика, выбор «поле + договор» и фильтр «поставка раньше даты». Ответы строятся из той же таблицы.

Ответы на учебном комплекте: STN-101 срок 30.04.2026 (допсоглашение № 1; проект № 2 предлагает 10.05.2026 и не действует); STN-102 сумма 840 000 ₽; STN-103 сумма «нет данных» (стоимость в приложении, которого нет в комплекте; лимит 600 000 ₽ не является ценой договора); раньше 01.04.2026 только STN-102 (20.03.2026), по нему есть несогласованный перенос на 27.03.2026 из письма поставщика.

## Как устроено

```
TXT ──> parseDocument: тип (договор / допсоглашение / проект / письмо), статус подписания,
        дата вступления в силу, номер договора, абзацы и предложения
    ──> extractField: шаблоны из FIELDS по каждому предложению, значение + цитата
    ──> analyze: условия договора, поверх них действующие на дату допсоглашения,
        остальное в «не согласовано», неясное в «требует проверки»
    ──> app.js: таблица, вопросы, исходные документы с якорями на абзацы
```

`checker.js` разбор (250 строк, без зависимостей), `app.js` интерфейс, `test/` автотесты, `documents/` учебный комплект.

Новое поле (например, ставка неустойки) добавляется одной записью в `FIELDS` в `checker.js`: шаблоны поиска, нормализация, формат вывода. Колонка в таблице и пункт в вопросах появляются сами.

## Ограничения

- Только TXT в UTF-8 или Windows-1251. OCR, PDF, DOCX не входят.
- Шаблоны рассчитаны на формулировки как в учебных документах: «стоимость ... составляет N рублей», «поставить ... не позднее ДД.ММ.ГГГГ», «изменить срок поставки на ...». Другая формулировка даст «нет данных», а не выдуманное значение.
- Тип документа определяется по заголовку, статус подписания по строке «Статус:», дата вступления в силу по фразе «вступает в силу ДД.ММ.ГГГГ».
- Документ привязывается к договору только по номеру вида `STN-101` в тексте. Нет номера или несколько номеров: предупреждение, а не догадка.
- Данные не сохраняются: после перезагрузки страницы файлы загружаются заново.

## Записка

**Пользователь.** Специалист по закупкам, который сверяет условия поставок по пакету документов: ему нужно быстро ответить, что действует на дату, и показать основание, не перечитывая всё.

**Пять вопросов клиенту перед развитием.**
1. В каком виде приходят документы на самом деле (TXT, DOCX, сканы) и из какой системы: СЭД, почта, папки?
2. Какие условия кроме суммы и срока сверяют регулярно: неустойка, оплата, аванс, этапы, спецификации?
3. Чем в вашем процессе подтверждается подписание и вступление в силу: ЭП, отметка в СЭД, скан? Можно ли доверять статусу в тексте документа?
4. Что делать при неясности: кто принимает решение и нужна ли отметка «проверено человеком» с журналом?
5. Сколько документов и пользователей, как устроены права доступа и нужно ли локальное развёртывание?

**Допущения.** Абзац = строка текста. Номер договора вида `ABC-123`. Суммы в рублях с НДС. Одно допсоглашение относится к одному договору. Если в силу вступили несколько подписанных допсоглашений, действует последнее по дате вступления; одна дата и разные значения дают «требует проверки».

**Метрики.**
1. Точность на размеченной выборке: доля полей, совпавших с ручной разметкой, и отдельно число значений, выданных при их отсутствии в тексте (цель 0).
2. Время сверки пакета документов закупщиком до и после, плюс доля значений, которые он исправил после проверки по источнику.

**Три ключевых решения и компромиссы.**
1. Правила, а не LLM. Плюсы: бесплатно, повторяемо, цитата всегда дословная, выдумать нечего. Минус: другой стиль формулировок требует новых шаблонов. Граница применимости: однотипные документы; для разнородных нужна LLM-экстракция с обязательной цитатой и проверкой, что цитата есть в тексте.
2. Всё в браузере, без сервера. Плюсы: открывается по ссылке, документы не покидают компьютер пользователя. Минус: нет хранения, истории и совместной работы.
3. Неясное помечается, а не угадывается: нет даты вступления в силу, нет статуса, несколько договоров в письме, разные значения в одном документе. Цена: больше ручных проверок, зато нет ложной уверенности.

**100 000 документов и права доступа.** Обработка уходит на сервер в очередь при загрузке; извлечённые факты хранятся в БД с привязкой к версии документа и абзацу. Связывание документов через поиск (полнотекстовый и векторный), а не только по номеру. Нестандартные формулировки разбирает LLM с проверкой цитаты, качество меряется на размеченной выборке. Права применяются на уровне индекса: факт виден только тому, кому виден исходный документ; просмотры и правки в журнале аудита.

**Три следующих улучшения по приоритету.**
1. Отметка «проверено» и ручная правка значения с журналом: замыкает сценарий сверки.
2. Новые поля тем же механизмом (неустойка, оплата, аванс) и выгрузка таблицы в Excel.
3. DOCX и PDF на входе, LLM-экстракция для нестандартных формулировок.

**Характерные запросы.**
1. «Посмотри вакансию и задание. Сначала задай вопросы; если понятно, как сделать быстро и правильно, делаем.» Агент разобрал документы, предложил правила вместо LLM и заранее перечислил ловушки: аванс и лимит бюджета не сумма договора, срок оплаты не срок поставки, письмо и проект не меняют условия.
2. «Нужно показать работающее по ссылке.» Агент изначально предлагал локальное приложение на Streamlit, которое проверяющий не откроет без установки. Переделали в статическую страницу с разбором в браузере на GitHub Pages.

**Ошибка ИИ и как поймали.** Первая версия делила текст на предложения по точкам и резала цитату внутри кавычек: у допсоглашения цитата обрывалась посреди новой редакции пункта. Заметили при прогоне страницы в браузере, исправили (внутри «...» не режем) и добавили тест на целостность цитаты. Там же нашли, что значение и ссылка на источник слипаются в одну строку.

**Проверка.** 15 автотестов: ответы на четыре вопроса, изменённое поле, новый договор того же формата, допсоглашение до и после даты проверки, допсоглашение без даты вступления в силу, документ без номера договора, дословность каждой цитаты, CRLF и BOM. Плюс прогон сценария закупщика в браузере, включая загрузку нового договора в Windows-1251.

**Затраты.** 15 минут работы с агентом из 4 часов: разбор задания и вопросы, код, тесты, проверка в браузере, README. Плюс моя приёмка перед отправкой. Не сделано: отметка «проверено», выгрузка в Excel, дополнительные поля.
